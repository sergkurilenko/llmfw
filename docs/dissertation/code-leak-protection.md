# Защита от утечки конфиденциального исходного кода в промпты: модуль LLM FW

Дата: 03.10.2026. Контекст: llmfw + LiteLLM (Generic Guardrail API), ООО «Код Безопасности».

## 1. Почему это главный модуль

- Исходный код — крупнейшая категория утечек в GenAI: 42% нарушений политик по данным
  Netskope Cloud and Threat Report 2026; 18.7% всех чувствительных данных, попадающих в
  ИИ-инструменты, по Cyberhaven 2026. По данным «Солар», объём данных российских компаний,
  уходящих в публичные нейросети, за 2025 год вырос в 30 раз; 8.5% запросов сотрудников
  содержат конфиденциальные сведения, включая исходный код.
- Прецедент: Samsung, апрель 2023 — три утечки исходного кода в ChatGPT за 20 дней.
- Регуляторика: проект требований ФСТЭК прямо запрещает передачу информации ограниченного
  доступа разработчику модели; режим коммерческой тайны (98-ФЗ); с марта 2026 — первые
  оборотные штрафы за утечки. Для компании-разработчика сертифицированных СЗИ и СКЗИ
  исходные тексты — информация ограниченного доступа по условиям сертификации.
- Канал, который обычные DLP закрывают плохо: вставка фрагмента, а не файла; переименование;
  частичные фрагменты; автоматическая отправка контекста IDE-ассистентами.

## 2. Модель угроз

Каналы попадания кода в промпт:
1. Ручная вставка в чат (самый частый).
2. IDE-ассистент (Copilot-подобные, Cursor, Continue), автоматически прикладывающий
   соседние файлы и весь буфер — большой объём, жёсткая латентность.
3. Вложения и файлы, архивы, диффы, патчи.
4. Скриншоты кода (поле `images` в запросе) — нужен OCR.
5. Логи, стек-трейсы, сообщения об ошибках с фрагментами кода и внутренними путями.
6. Дробление: один файл по 20 строк в десяти сообщениях (обход порога).
7. Преобразования: переформатирование, переименование идентификаторов, удаление
   комментариев, перевод на другой язык программирования, пересказ алгоритма словами.

Нарушители: небрежный сотрудник (основной), автоматика ассистента, инсайдер,
целенаправленно обходящий детектор (модель Mossad: автоматический обход MOSS).

Что считать конфиденциальным (уровни):
- T0 — криптографические модули и ядро сертифицированных продуктов: только блокировка.
- T1 — остальной продуктовый код: блокировка для внешних моделей, санитизация или
  маршрутизация на on-prem модель.
- T2 — тесты, скрипты сборки, внутренняя документация: санитизация и журнал.
- Не конфиденциально: вендорённые open-source зависимости, публичные зеркала,
  стандартный шаблонный код. Их обязательно исключать из индекса (SBOM/лицензионный
  сканер до индексации), иначе ложные срабатывания похоронят продукт.

Куда идёт запрос тоже важно: зона доверия целевой модели (on-prem / российское облако /
зарубежная API). LiteLLM передаёт поле `model`, по нему FW применяет разную политику.

## 3. Методы обнаружения (четыре слоя, от дешёвого к дорогому)

### 3.1. Обнаружение кода и секретов (детерминированно, < 1 мс)
- Есть ли код: ограждённые блоки, плотность символов `{};()=`, отступы, ключевые слова;
  определение языка (аналог Purview «Source Code»: 23 языка, частичный код).
- Секреты: regex + энтропия (правила gitleaks/trufflehog): ключи API, приватные ключи,
  пароли в конфигурации, токены. Любое совпадение — немедленная блокировка, независимо
  от остального.

### 3.2. Лексические маркеры принадлежности (словарь, < 1 мс)
Внутренние пространства имён и пакеты, имена продуктов и модулей, внутренние хосты и
домены, ключи задач трекера, заголовки с copyright, пути сборки, имена внутренних библиотек.
Взвешенный словарь (IDF по публичным корпусам), чтобы «Continent» в тексте о географии
не блокировался. Дёшево и объяснимо; ловит большинство небрежных вставок.

### 3.3. Отпечатки кода — членство в кодовой базе (winnowing, линейное время)
- Нормализация: удаление комментариев и пробелов, абстракция идентификаторов и литералов
  (тип-1 и тип-2 клоны ловятся гарантированно).
- Winnowing (Schleimer, Wilkinson, Aiken, 2003; основа MOSS): хэши k-грамм токенов, окно w,
  выбор минимума в окне; гарантия: любое общее подстрочное совпадение длиной ≥ t = w + k − 1
  токенов обнаруживается, короче k — игнорируется. Типично k = 25–50 токенов, w ≈ k.
- Индекс строится в CI из репозиториев компании; хранит только HMAC-хэши отпечатков с
  секретным ключом (ключ на FW, не в репозитории) и ссылку (репозиторий, файл, строка)
  для SOC. Исходный код на шлюз не попадает.
- Фильтр общности: отпечатки, встречающиеся в публичных корпусах (The Stack v2) или
  в слишком многих файлах (шаблоны, лицензии, геттеры), исключаются из индекса.
- Оценка: доля отпечатков запроса, найденных в индексе, с учётом уровня T файла;
  длина максимального совпадения.
- Оценка объёма: 10 млн строк ≈ 10^8 токенов → ~10^8 k-грамм → winnowing оставляет
  ~2/(w+1) → ~5·10^6 отпечатков × 16 байт ≈ 100–200 МБ в памяти. Обновление — инкрементально
  по коммитам.

### 3.4. Семантическое членство (эмбеддинги, миллисекунды)
Для переименованных, частично переписанных и переведённых фрагментов (тип-3/4 клоны):
- Энкодер кода on-prem (UniXcoder/CodeT5+/SourceTracker-подобный 300M), чанки по функциям.
- Двухступенчатая схема как в HybridSourceTracker (векторный поиск → переранжирование
  winnowing): на 100k сниппетов превосходит чистый winnowing на адаптированных
  (переименованных) фрагментах от 60 токенов на величину до 5.4% при логарифмической
  сложности запроса. Здесь та же схема применяется к закрытой базе.
- Порог калибруется на публичном коде так, чтобы гарантировать FPR (конформный порог).
- Индекс эмбеддингов — объект атак восстановления (vec2text: 92% точного восстановления
  32-токенных текстов; ALGEN, ZSinvert, Zero2Text — без обучающих пар, чёрный ящик).
  Нужна защита: квантование, целевой шум (TextCrafter, SPARSE), «необратимые» проекции.
  Это прямое применение задела по защите от инверсии эмбеддингов.

### 3.5. Сессионный уровень (дробление)
Накопление совпадений по пользователю и по `litellm_trace_id`: последовательный критерий
(SPRT/CUSUM) по потоку совпадений отпечатков с контролируемой частотой ложных тревог.
Один фрагмент в 15 строк не сработает, десять подряд из одного файла — сработают.

### 3.6. Опционально: происхождение с конечной точки
Подход Cyberhaven (data lineage): агент на рабочей станции знает, из какого файла и
приложения скопирован текст. У компании есть свой агент (Secret Net Studio): метка
происхождения буфера обмена в заголовке запроса даёт FW сильный априорный признак и
закрывает случай «код переписан до неузнаваемости». Уникальная связка для рынка РФ.

## 4. Решение и действия

Итоговая оценка: калиброванная вероятность «фрагмент принадлежит защищённой базе» плюс
уровень T и зона доверия модели → одно из действий:
- BLOCKED — T0 всегда; T1 для внешних моделей. Пользователю — общее сообщение, в SOC —
  репозиторий/файл/строки и пользователь.
- GUARDRAIL_INTERVENED (санитизация) — обратимая псевдонимизация: идентификаторы →
  нейтральные имена, внутренние пути/хосты → плейсхолдеры, комментарии с внутренними
  сведениями → удалены, строковые литералы → маски; таблица замен хранится на FW по
  `litellm_call_id`, в post_call ответ модели депсевдонимизируется (в стриме —
  `streaming_transform_mode: incremental_diff`). Утилита сохраняется: сильные модели
  держат ~90% Pass@1 на обфусцированном коде (arXiv 2609.04220).
- Перенаправление на on-prem модель — через тонкий in-process хук LiteLLM
  (`async_pre_call_hook` может менять `data["model"]`), внешний сервис менять модель не может.
- Эскалация в SOC/SIEM — по сессионному критерию и для T0.

## 5. Интеграция в llmfw/LiteLLM

- pre_call: `structured_messages` (все роли, включая tool и system), `texts`, `images` (OCR),
  `model` (зона доверия), `request_data` (user/team/org для политик и сессий), `litellm_trace_id`.
- post_call: обратная псевдонимизация, контроль, что модель не вернула «восстановленный»
  внутренний код из контекста.
- Бюджет латентности: чат — до 50 мс; IDE-автодополнение — до 15–20 мс (слои 3.1–3.3
  укладываются, 3.4 — асинхронно или только для чата/крупных вставок).
- Индекс: сборка в CI по защищённым репозиториям, подпись, доставка на FW, ротация ключа HMAC.

## 6. Что уже есть и чего нет (новизна)

| Что есть | Ограничение |
|---|---|
| DLP-отпечатки (Symantec IDM, Forcepoint): нормализация + необратимый хэш | документы, не код; нет устойчивости к переименованию и нет сессионного уровня |
| Purview «Source Code» classifier (23 языка, частичный код) | «это код» ≠ «это наш код» |
| Cyberhaven lineage | нужен агент на каждой точке; не видит IDE-ассистентов через API |
| CodeCloak (DRL-манипуляции промпта IDE-ассистента) | утечка снижена до 40% при 70% сходства подсказок; нет понятия «чей код», нет гарантий |
| CodeCipher (обучаемая обфускация токенов) | защищает от провайдера, не решает обнаружение |
| HybridSourceTracker (вектор + winnowing) | провенанс LLM-кода против The Stack; индекс открытый, нет защиты индекса, нет сессий |

Свободные ниши:
1. Членство в закрытой кодовой базе при преобразованиях (переименование, частичность,
   перевод) с гарантией обнаружения для класса преобразований и гарантией FPR на публичном
   коде; устойчивость к целенаправленному обходу (Mossad).
2. Приватность индекса на шлюзе: ключевые отпечатки + эмбеддинги, устойчивые к инверсии,
   с измеренной границей утечки при компрометации шлюза.
3. Санитизация с сохранением полезности: кривая «утечка — полезность» на задачах
   исправления, объяснения и дополнения кода; обратимость.
4. Сессионное последовательное обнаружение дробления с контролем ложных тревог.
5. Бенчмарк: «псевдозакрытая» база из отложенных репозиториев + набор преобразований +
   трудные негативы (вендорённый OSS, StackOverflow, шаблоны) + внутренняя оценка на
   реальных (обезличенных) запросах сотрудников.

## 7. Место в диссертации

Вариант А (рекомендую): этот модуль — центральная прикладная глава темы про LLM FW с
калиброванным ядром решений. Вопрос «принадлежит ли фрагмент защищённой базе» — один из
типизированных выходов ядра, но с собственным детерминированно-нейросетевым бэкендом.
Положения П2–П4 из плана LLM FW дополняются: гарантированное обнаружение/FPR для кода,
приватность индекса (инверсия эмбеддингов), санитизация с обратимостью.

Вариант Б: самостоятельная тема
«Методы предотвращения утечек исходного кода ограниченного доступа через запросы
к большим языковым моделям» (2.3.6). Плюсы: максимальная продуктовая привязка, уникальная
новизна, прямое использование первой темы (защита от инверсии эмбеддингов). Минус: уже
обсуждённые положения про инъекции и гард-модели уходят в обзор.

## 8. План работ

1. (4 нед.) Слои 3.1–3.3: детектор кода, секреты, маркеры, winnowing-индекс из CI, политика
   по уровням и зонам доверия, BLOCKED/журнал. Это уже рабочий продуктовый MVP.
2. (4 нед.) Санитизация с обратимостью, post_call, стриминг; OCR для изображений.
3. (6 нед.) Слой 3.4: энкодер, ANN-индекс, калибровка порога на публичном коде,
   защита индекса от инверсии, атаки на индекс.
4. (4 нед.) Сессионный критерий, интеграция с SIEM, бенчмарк и отчёт; опционально —
   метка происхождения от Secret Net Studio.

Критерии приёмки: обнаружение ≥ 99% фрагментов ≥ 50 токенов из T0/T1 при переформатировании
и переименовании; FPR ≤ 0.5% на вендорённом OSS и публичных сниппетах; p95 ≤ 20 мс для
слоёв 3.1–3.3; восстановление кода из индекса атаками инверсии — не выше заданной границы;
полезность ответов на санитизированном коде ≥ 85% от исходной.

## 9. Риски

- Ложные срабатывания на OSS и шаблонах — лечатся исключением вендорённого кода и фильтром
  общности; проверять на первом же пилоте.
- Обход пересказом алгоритма словами — не ловится отпечатками; частично — семантикой и
  меткой происхождения; честно описать границу.
- Правовые: мониторинг запросов сотрудников требует локальных актов и уведомления;
  журнал не должен хранить сам код (только хэши и ссылки).
- Компрометация шлюза: индекс должен быть бесполезен без ключа; эмбеддинги — защищены.
- Латентность на IDE-трафике; семантический слой — асинхронно.
